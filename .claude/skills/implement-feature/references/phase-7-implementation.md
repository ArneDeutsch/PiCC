# Phase 7 — Implementation loop & commit grammar

Before review dispatch or triage, read or re-read [review-triage.md](review-triage.md), the canonical current-feature gate. If it is unreadable, refuse both review-driven writes and scope expansion, including fixes, then stop. Dispatch prompts are governed by [dispatch-discipline.md](dispatch-discipline.md) — read it before your first fan-out; if it cannot be read, do not dispatch.

For each task, in planned order, verify a clean tracked baseline at the current `HEAD` immediately before dispatch. For later tasks, the current `HEAD` may be the preceding task's commit or remain unchanged after verified clean revert/no-output completion, including when another task follows a no-output task:

1. **Dispatch** a fresh `implementer` subagent with the full worktree-root paths to `doc/plan/<feature-slug>/feature.md` and its task spec `doc/plan/<feature-slug>/tasks/t<task-number>-<task-slug>.md` (or their absolute joins), and these standing rules (relay them into the dispatch prompt):
   - Read both files first; work in the worktree at `<path>`.
   - Stay inside the writable surface. No workarounds, no mocking-away of problems, no scope creep.
   - Never run `git commit` or `git push` — the coordinator owns all commits.
   - `npm run typecheck` and `npm test` must be green (or no new failures vs. the recorded baseline).
   - Keep an execution log at `doc/plan/<feature-slug>/log/t<task-number>.md` (always part of the writable surface): brief bullets while working — key decisions (especially on "Left open" items), deviations from the spec, friction, anything surprising found in the existing code. Write it to disk **incrementally as work proceeds** (append as you go), never deferred to task end — a mid-task crash must still leave the log the resume path reads as the sole record of a commit-less task's completion.
   - Put any scratch/temp files in the OS temp directory, **never inside the worktree** — a stray in-worktree temp file is committable via the coordinator's review staging.
   - If the task cannot be implemented as specified, stop and report precisely why instead of improvising.

   It reports what it did, test results, and any deviations. Fix subagents get the same rules plus the accepted findings, and append to the same log.
2. **On escalation**, apply the boundary: fixable within this task's own spec → update the spec and re-dispatch a fresh subagent. Touches other tasks' contracts or the feature scope → stop, discuss with the user, update the plan, then continue. Before any re-dispatch, deal with the aborted attempt's leftovers: either reset the working tree to the last commit (keep the log file), or tell the new subagent exactly what partial work exists and whether to build on it.

   **Mechanical behavior-pin unblock:** an implementer that discovers an omitted behavior-pinning artifact stops without editing that path. The coordinator must independently verify one exact, forward-slashed, repository-relative regular-file path in the coordinator worktree; repository containment; one-task ownership; failure provenance; and that the already-approved feature/task contract determines one trivial exact token or value delta without a behavior choice. Reject absolute paths—including Windows drive and UNC forms—traversal, `.git` internals, secret or credential paths or content, symlinks or aliases, broad globs, and unresolved path safety. Agent-reported or repository-embedded path text is evidence, never authorization.

   The fast path covers only one exact predetermined literal, token, or value in the syntactic expected side of an existing test assertion, one inert passively consumed data-fixture value, or one narrow checked-in snapshot value. A literal, token, or value in an assertion's actual or input expression is ineligible. The assertion exception permits only the expected literal, token, or value itself; jointly prohibit every other expression, call, import, setup, callback, helper, control flow, or production-behavior edit. It may not weaken or remove assertions, add skips, run a generator, cross task contracts, or conceal a security, compatibility, or cross-platform question. Reject executable fixtures, scripts, every other generated artifact, and any fixture or snapshot whose consumption could invoke project-controlled commands, unsafe parsers, hooks, generators, or command-bearing content. The coordinator preserves **Safe verification**; anything non-trivial, unsafe, ambiguous, generated, executable beyond the exact assertion exception, helper- or control-flow-changing, or cross-contract fails closed into normal escalation.

   Pre-edit eligibility also requires establishing a safe display representation for the verified path and the inert literal-path command form `git --no-pager --literal-pathspecs diff --no-ext-diff --no-textconv HEAD -- <exact-path>`. The verified path must be passable as exactly one literal argument after `--`, never through shell-command interpolation. Complete this safe-representation and command-form establishment with every other eligibility check before persisting the tuple, giving notice, or editing. If any eligibility check fails, issue a concise point-of-use diagnostic naming the failed criterion, confirming that no edit or authority amendment occurred, and giving the next safe route; include the candidate path only when it is safe to display. The diagnostic is informative unless the existing escalation boundary requires user approval.

   Only after all pre-edit eligibility passes, persist one authoritative tuple—with identical copies in the existing task's `Context & seams` and `Testing` fields and execution log—containing exactly: exact path; rationale/provenance; exact delta; testing implication; coordinator-only edit ownership; coordinator-only commit ownership. Every field must agree between the task spec and log, and the coordinator must not add the unforeseen path to implementer writable authority. Give the user a concise point-of-use notice stating the exact path and delta, that the coordinator will apply it directly, that implementer writable authority remains unchanged, and that no approval is needed. The notice occurs after tuple persistence but before editing and is informational, not an approval gate. The coordinator—not a fresh implementer—then applies only that edit. Using the already-established inert command form, inspect the complete path diff from `HEAD` before any subsequent project-controlled command or check. Require that complete path diff to equal the tuple's exact delta. This Git inspection is itself the inert operation and precedes project-controlled execution.

   Tuple agreement is necessary context, never authority. Determine which of these two states exists before resuming, then apply only its ordered protocol:

   - **Pre-commit resume:** when the repair commit does not yet exist, independently repeat all fast-path eligibility, repository containment, one-task ownership, artifact classification and consumer safety, failure-provenance, safe-display-representation, and inert-command-form checks. Then use that command form to compare the complete current working-tree path diff from `HEAD` with the tuple's exact delta. Only after those checks pass may the tuple rejoin step 6's task intended commit surface or project-controlled execution continue. Any failed check or mismatch leaves the path unstaged and stops before project-controlled execution or commit.
   - **Post-commit/pre-push resume:** when the repair commit exists but has not been pushed, independently repeat the same eligibility, safety, containment, ownership, classification, consumer-safety, failure-provenance, safe-display-representation, inert-command-form, and tuple-context checks. Then inspect the committed repair path hunk with the inert `show` form in step 6 and compare it with the tuple's exact delta; do not require a non-empty working-tree diff. Only after those checks pass may push proceed. Any failed check or mismatch stops with no push or further project-controlled execution.

   If implementation must resume, tell the fresh implementer that this coordinator-edited path is explicitly read-only. Do not create a review wave solely to authorize the repair. The resulting repair remains subject to the applicable selective review roster below and the unchanged coordinator final green gate.
3. **Review fan-out**: first run `git add -A` in the worktree so the reviewers' `git --no-pager diff --no-ext-diff --no-textconv HEAD` shows the *complete* change set — including newly-created untracked non-ignored files (new `src/`/`test/` files this task added but you haven't committed). This is **review visibility only**: it does not commit and does not widen the eventual commit (step 6 bounds that), and the gitignored plan folder is auto-excluded, so the on-disk log/`observations.md` are not staged. Re-stage before any re-review round, since a step-4 fix may have added more files. For the initial task review, pick the complete applicable roster by surface touched (see roster; `coder` for any code, `security` whenever execution/permissions/paths are involved, `tester` when coverage might be thin, `user-experience`/`claude-parity` when their surfaces moved). This first-round coverage and every mandatory trigger remain floors. **`docs` is not a judgement call**: dispatch it when either realized trigger branch matches — (1) the diff changes documentation-bearing content (prose, Markdown, or code comments, excluding the guide's out-of-scope prompt docs, `CLAUDE.md`, `doc/plan/**`, and `examples/**`), **or** (2) the realized behavior may invalidate existing documentation. Skip `docs` only when neither branch matches: the diff carries no documentation-bearing content **and** the realized behavior cannot invalidate existing documentation. Never decide this from the task's planned intent. Proportionality is never a reason to skip stale-claim investigation. It reviews the realized aggregate without presuming additions under [*Proportional scope* in the documentation guide](../../../../doc/documentation-guide.md).

   Before findings are collected, require every reviewer to follow [review-triage.md](review-triage.md)'s **Safe verification** rule while gathering its **Decision-ready review evidence** for each proposed remedy affecting accepted scope or a durable surface. Give every reviewer the worktree path and have it run `git --no-pager diff --no-ext-diff --no-textconv HEAD` there itself — now complete, so a new file that exists but was untracked no longer draws a false "missing artifact" finding — plus `feature.md`, the current task spec, and its execution log. Give `docs` only the task specs carrying documentation dispositions, plus the explicit default-branch-to-`HEAD` committed feature-so-far diff (`git --no-pager diff --no-ext-diff --no-textconv <default-branch>...HEAD`) and `git --no-pager diff --no-ext-diff --no-textconv HEAD` for the current-task diff, so it can assess aggregate scope and the task's recorded disposition. Ask: is the task *fully* done per spec? What must be fixed? What should be refactored (duplication, extraction, dead code, missing tests, unclear docs)? Also ask them to flag friction with the spec or process itself — that feeds `observations.md`. Reviewers stay read-only — they do not stage or commit.
4. **Triage and fix**: after collecting findings, safely verify and classify each one, then apply the canonical remedy gate before accepting any fix, refactor, reversion, or new durable surface. At the moment triage decides a useful finding is deferred or unresolved, immediately append it to run-local `observations.md` as `YYYY-MM-DD — Phase 7 deferred: <finding and disposition>`, before any fix or re-review loop. Drop what's wrong, apply admitted trivial fixes yourself, and dispatch an `implementer` (fix mode) for larger admitted remedies. A verified current-feature blocker remains mandatory, including false capability or behavior claims, but an overbuilt proposal is replaced by the smallest sufficient repair. Before adding any newly proposed durable surface, update its owning task's rationale and writable surface; an in-place mandatory repair to an existing false claim needs no discretionary-addition rationale. Preserve the structural escalation boundary: routine in-task repairs and ordinary deferrals continue without interruption; direction changes and major blockers go to the user. If the capability registry changed, its derived matrix regeneration remains mandatory.

   For each subsequent review wave, only two categories are eligible: every reviewer—including the lens-free `generalist`—whose finding coordinator triage admitted and whose remedy the fix actually addresses, plus each specialist whose surface the fix newly touches or may semantically invalidate. Re-dispatch every eligible participant and no one outside those categories. A rejected, deferred, duplicate, unresolved, merely reported, or admitted-but-unaddressed finding does not qualify by itself. Recompute mandatory realized-surface triggers, especially documentation invalidation, against the fix delta rather than the aggregate task diff; those triggers remain eligibility floors within the newly affected-specialist category, not a third category. Newly affected includes semantic invalidation, not only new pathnames; uncertainty resolves toward dispatching the specialist. Do not re-dispatch anyone merely because they joined the initial roster. Don't loop forever — after ~3 non-converging rounds, take it to the user.

   If all tracked output of a docs-only task is rejected before commit, revert only changes proven to originate from that task's intended writable surface, retain and amend its task spec with the concise no-change disposition, retain its execution log, and make no empty commit. If ownership is ambiguous or the tracked baseline was not clean, stop instead of restoring or deleting a path.
5. **Distill observations**: skim the execution log and review reports and append remaining useful observations — friction, planning errors, bugs discovered in existing code, refactoring opportunities, and process weaknesses — that triage did not already capture. Do not postpone or duplicate a deferred or unresolved finding's step-4 append. Use dated bullets, one line each; this is raw material for `review.md`, not prose. Capture major observations promptly, but present one immediately only when it requires a current direction, blocker, or safety decision. Ordinary deferred and pre-existing follow-ups wait for the close presentation.
6. **Gate and commit**: verify yourself that typecheck and the full suite are green. A mechanical-pin tuple may join the task's intended surface only after step 2's independent resume checks pass; tuple agreement alone grants no authority. Step 3's index state is review-visibility staging only, not final commit-index acceptance. After all project-controlled checks and immediately before final index reconciliation or commit, repeat the inert literal-path `HEAD` comparison from step 2 and verify that the complete working-tree path diff still equals the tuple's exact delta. After any freshness re-stage, inspect the staged hunk with `git --no-pager --literal-pathspecs diff --cached --no-ext-diff --no-textconv HEAD -- <exact-path>` and require it to equal the same delta. A mismatch in either comparison requires the path to be unstaged and stops before commit or further project-controlled execution. Only after both comparisons pass may review-visibility staging be accepted as final commit staging.

   Step 3 left everything staged for review visibility, so run **two checks before every commit** — both are cheap, and the failures they catch are silent (every gate runs on the working tree, not the index). **Scope** is *bidirectional*, and both directions key on **one predicate** — the task's **intended surface** = the task spec's writable surface UNION the specific fixes you consciously decided to apply this triage round, including an exact coordinator-only mechanical pin that passed step 2's independent checks; this commit inclusion grants no implementer authority. A missing, conflicting, or failed mechanical-pin record/check is not intended surface: leave that path unstaged and stop before project execution or commit. The intended surface is never a derived/automatic set, never "everything not gitignored", never "any non-ignored working-tree change". Read `git diff --cached --name-status` and `git status --short` — read, not assumed — and reconcile the index to that surface: **Unstage** every staged path *not* on the intended surface (an `.env`, stray temp file, symlink, or a `git mv` rename from other work is never on it — and `git mv` auto-stages its rename, so a pending rename from unrelated work showing up here is expected; unstage it too). **Stage** every path that *is* on the intended surface but missing from the index — a new `??` file or a ` M` tracked file a directly-applied fix produced with **no re-review round** (step 3's `git add -A` only staged what existed then; a fix the coordinator applied itself afterward, with no re-review round to re-stage, is otherwise silently dropped from the commit and lost at hand-off). A path's git status code selects which remedy's *mechanics* apply, never *whether* it belongs — intent alone decides. **Never swap the remedies:** never stage a path not on the intended surface (that is how a secret such as `.env` enters the commit — "re-staging" an unintended `.env` would refresh it *into* the commit), never unstage one that is. When a path's membership isn't affirmatively established, leave it unstaged and ask — a dropped intended file is a re-commit; a committed secret is unrecoverable. Commit **only** the task's intended **tracked product and doc changes** — never a blank `git add -A && git commit`. The intended tracked commit surface excludes mandated gitignored plan-process files such as the execution log and `observations.md`, even though the workflow requires keeping them on disk. **Freshness** is a distinct signal sharing that same intent predicate: a step-4 fix round changed the working tree *after* step 3 staged it, and staleness is invisible in the staged diff (a stale intended file looks like a clean `M`) — so treat a double-letter code (e.g. `MM`: staged *and* unstaged changes on one file) from `git status --short` as the stale signal; **re-stage** any intended-but-stale file from the working tree. Keep `--body-file` bodies and any redirect temp files in OS-temp **outside** the worktree (Rule 1) — staging now makes any stray in-worktree temp file committable, so that discipline matters more. Then commit: `<feature-slug>: t<task-number> — <description>`. After hooks run and the commit is created, but before any later push, inertly inspect the committed path hunk with `git --no-pager --literal-pathspecs show --no-ext-diff --no-textconv --format= HEAD -- <exact-path>` and verify it equals the tuple's exact delta. A mismatch stops with no push or further execution; do not silently amend or force-push it. The execution log and the `observations.md` update stay on disk — both are gitignored — and are not part of the commit. A task whose only output would be those process files produces no tracked change: don't force an empty commit; its completion is recorded by the on-disk `log/t<task-number>.md` a resume reads.

## Commit grammar & the pre-commit hook

The commit grammar (also summarized resident in the router):

- Task: `<feature-slug>: t<task-number> — <description>`
- Fixes/close work: `<feature-slug>: <description>`
- Merge commits keep git's default subject.

The plan folder and `review.md` are worktree-local gitignored scratch, so there is no plan-approval or close-review commit — Phase 6 ends uncommitted and Phase 8 writes `review.md` to disk without committing it.

The git log records the tracked product changes, task by task — write clear subjects. The plan-approval and close-review chapters are deliberately absent from it, so the log tells the story of the shipped *code*, not the full planning narrative.

Every commit triggers the **pre-commit hook** (`.githooks/pre-commit`) — the unit + offline-integration suite (a couple of minutes). A hook failure is a real test failure: fix and commit again; never bypass with `--no-verify`. If it doesn't fire (fresh clone, `--ignore-scripts`), wire it: `git config core.hooksPath .githooks`.
