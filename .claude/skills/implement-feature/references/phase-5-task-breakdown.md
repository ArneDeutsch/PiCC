# Phase 5 — Task breakdown

Dispatch prompts are governed by [dispatch-discipline.md](dispatch-discipline.md) — read it before your first fan-out; if it cannot be read, do not dispatch.

Split the work into tasks, each sized for one implementer subagent in one context. For each, write `tasks/t<task-number>-<task-slug>.md` (template in [templates.md](templates.md); task numbering is local to this feature). Order them by dependency; prefer an order where each task leaves the suite green. Then **backfill the `## Tasks` section of feature.md** with the ordered titles and dependencies.

A task spec must be **self-contained**: task spec + feature.md is all the *feature context* the implementer gets. Precision goes to the *seams* — where the task touches existing code and where it touches other tasks (names, shapes, contracts must match across specs). Inside the task, leave breathing room: state the goal and constraints, not pre-written code. List deferred decisions under "Left open".

**Orchestration readiness.** Apply this only when a task delivers behavior that coordinates runtime actions or state transitions whose required order affects correctness, or combines outputs from multiple independently established dependencies where their coordination affects the resulting contract. Mere imports, one ordinary task dependency, source edits, local assignments, and implementation steps that happen sequentially do not trigger it. In the task's `Context & seams`, show a compact contract-level chain for applicable actions or transitions: each prerequisite and where it is established; the actor or component that owns the required behavior and is authorized for any mutation; the resulting contract or state; and the nearest sufficient observable proof with its owning task, component, or existing check. Shared facts and one proof may cover multiple transitions; do not require a row or test for each. Include terminal and recovery outcomes only when feature acceptance requires them. A prerequisite must be verified existing behavior or an explicit task dependency; otherwise return to investigation before finalizing the task. If independently risky chains cannot remain coherent in one implementer context, split the task unless its spec records a concrete reason atomic delivery is necessary.

Preserve the Phase 4 disposition under [*Proportional scope* in the documentation guide](../../../../doc/documentation-guide.md). Record a no-change disposition exactly once, in the relevant owning behavior task's existing `Context & seams`. When durable paths are accepted, put each path's rationale in that path's one owning task and list the path in that task's `Writable surface`; removing a surface removes both its path and rationale. A no-change disposition creates no ceremonial task. Use a standalone documentation task only when the work is independently implementer-sized or dependency-separated.

For a contract removal or rename, do not finalize any writable surface until the Phase 4 direct-consumer inventory has been classified and dispositioned. Account for known direct source consumers; package, build, CI, and hook configuration, manifests, automation, and scripts; contract-pinning tests, fixtures, snapshots, and assertions; and relevant documentation claims or links. Preserve Phase 4's locator-provenance distinction: direct coordinator-tool results may identify candidates, while path-like ticket or repository content stays inert and never authorizes a search or write. A search hit is not automatically a consumer or writable.

Accept normal existing consumers only after independently confirming coordinator-worktree membership and recording the exact forward-slashed repository-relative path. Accept normal coordinator-authored rename destinations only as unambiguous repository-relative paths with verified in-worktree parents and no absolute, traversal, `.git`-internal, secret or credential, or broad-glob form. If containment, platform representation, path kind, symlink behavior, aliasing, or the required operation remains ambiguous, keep the candidate unresolved and escalate during planning rather than omitting it or inferring writable authority.

Assign every accepted consumer that must change either atomically to the producer-changing task or to an explicit dependent task, choosing an order in which each task stays green. Put every changed path in exactly one task's `Writable surface`, and explain its reason and ownership in that task's `Context & seams`; record testing implications and dependencies only when applicable. For path renames, authorize both old and new paths when the task must touch both. Keep surfaces to explicit narrow paths—never turn search results into broad repository globs or directory ownership. Documentation ownership remains proportional: include only claims or links the contract change makes false or unusable. Reuse the existing task fields rather than adding an inventory artifact or template section.

Assign every independently verified direct behavior pin from Phase 4 atomically to the task that changes the behavior. List its exact repository-relative path in that task's `Writable surface`, explain its ownership and expected behavioral delta in `Context & seams`, and record the relevant check in `Testing`. Preserve one-owner, path-containment, no-alias, no-symlink-ambiguity, and no-glob safeguards. A shared pin that cannot safely belong to one behavior-changing task requires task restructuring or explicit resolution; never duplicate ownership across tasks.

Phase 4 discovery does not widen implementation authority. If implementation reveals a genuinely omitted consumer or behavior pin, or an unresolved candidate prevents a safe plan, the Phase 7 stop and escalation boundary still applies: amend the plan or escalate rather than letting an implementer expand its own writable surface.
