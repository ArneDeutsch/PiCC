# Phase 8 — Feature close review

Before review dispatch or triage, read or re-read [review-triage.md](review-triage.md), the canonical current-feature gate. If it is unreadable, refuse both review-driven writes and scope expansion; also refuse close fixes, removals, and new tasks, then stop. Dispatch prompts are governed by [dispatch-discipline.md](dispatch-discipline.md) — read it before your first fan-out; if it cannot be read, do not dispatch.

When all tasks are complete and all retained tracked outputs are committed, review the whole feature against feature.md. The initial close review keeps the complete applicable roster, coverage, depth, and mandatory triggers. Before findings are collected, require every reviewer to follow [review-triage.md](review-triage.md)'s **Safe verification** rule while gathering its **Decision-ready review evidence** for every proposed remedy affecting accepted scope or a durable surface:

- Fan out the full relevant roster, always including `docs`, over the complete feature diff (`git diff <default-branch>...HEAD`) + `doc/plan/<feature-slug>/feature.md` and all task specs carrying documentation dispositions: is the WHAT fully delivered? Anything half-done, inconsistent, undocumented, or excessive? The docs reviewer validates both currentness and the complete aggregate under [*Proportional scope* in the documentation guide](../../../../doc/documentation-guide.md), without presuming additions.
- Add one adversarial completeness check (`generalist`): "what would a skeptical reviewer of the PR find missing?"

Integrate. After collecting findings, safely verify and classify each one, then apply the canonical remedy gate before any close fix, corrective removal, new durable surface, or new task. At the moment triage decides a useful Phase 8 finding is deferred or unresolved, immediately append it to run-local `observations.md` as `YYYY-MM-DD — Phase 8 deferred: <finding and disposition>`, before corrective work or new-task creation. Do not ordinarily present a deferred or follow-up finding yet; reserve ordinary follow-up presentation for one close pick-list: proposal-gated and assessed when the GitHub path is available, or every eligible still-actionable finding explicitly unassessed when it is unavailable. Surface a finding immediately only when it requires a current direction, blocker, or safety decision under the existing escalation boundary, after capturing it in `observations.md`. A verified current-feature blocker cannot remain unresolved at completion. Remove already committed aggregate excess through a reviewed corrective commit; this corrective removal remains mandatory, while the gate selects the smallest safe removal and confirms no accepted obligation or proof is lost. At the same time, remove each rejected path and its rationale from the owning task spec. Preserve the dispositions for remaining accepted surfaces, or record a concise no-change disposition when none remain. A small justified new durable surface is a close fix owned by the relevant completed task: record its rationale and path in that task's spec and writable surface, append its execution log, apply and review the change with Phase 7 fix discipline, commit it with the feature-fix grammar (`<feature-slug>: <description>`), then rerun the complete-feature review. An in-place small repair to an existing false claim follows the same fix discipline but needs no discretionary-addition rationale. Create a new task and run it through Phase 7 ([phase-7-implementation.md](phase-7-implementation.md)) only when the work meets Phase 5's threshold of being independently implementer-sized or dependency-separated; continue task numbering and update feature.md's `## Tasks`. If the gap questions the WHAT/WHY, talk to the user.

After any close fix, re-review with complete-feature context, but only two participant categories are eligible: every reviewer—including the lens-free `generalist`—whose finding coordinator triage admitted and whose remedy the fix actually addresses, plus each specialist whose surface the fix newly touches or may semantically invalidate. Dispatch every eligible participant and no one outside those categories. A rejected, deferred, duplicate, unresolved, merely reported, or admitted-but-unaddressed finding does not qualify by itself. Recompute mandatory realized-surface triggers, especially documentation invalidation, against the close-fix delta rather than aggregate feature paths; those triggers remain eligibility floors within the newly affected-specialist category, not a third category. Newly affected includes semantic invalidation, not only new pathnames; uncertainty resolves toward dispatching the specialist. Do not re-dispatch anyone merely because they joined the initial roster, and do not narrow the complete feature diff and specification context supplied to those selected.

Also make sure the repo's own records are current before closing: repair invalidated docs, and run `npm run gen:capabilities` if the capability registry changed. Required capability regeneration is never optional under proportional scope; this is the backstop the `docs` reviewer should already have enforced.

Before asking the user to close the feature, write the feature's `review.md` (template in [templates.md](templates.md)) by distilling `observations.md`, the task logs, and your own judgment of the cycle. Every still-useful deferred Phase 6, 7, or 8 finding that warrants follow-up must appear specifically under `Bugs discovered` or `Proposed follow-ups`. This is a **run-local staging record**, written to disk but not committed and lost with worktree cleanup; it is not durable cross-feature tracking. After `review.md` is prepared, invoke the existing per-item offer in [phase-8-file-finding.md](phase-8-file-finding.md). When its GitHub path is available, the proposal gate assesses the findings before one coherent assessed pick-list; when unavailable, the offer skips scoring and presents every eligible still-actionable finding once in one coherent explicitly unassessed pick-list with filing unavailable. Durable cross-feature tracking requires either a new GitHub issue filed with user approval or an existing issue the user explicitly confirms is equivalent and the workflow reuses under Rule 9. A candidate near-match or search hit alone is not durable tracking; a finding with neither outcome remains run-local and is lost with cleanup.

The ticket-path close hooks (close-vs-keep-open judgement + write preview) and the either-path issue-filing offer run inside this same close gate. Their full text lives split by path: the ticket-only close judgement in [phase-8-ticket-close.md](phase-8-ticket-close.md) (loaded only on the ticket path), and the path-independent issue-filing offer linked above. The nine write-discipline rules both obey are the floor in [ticket-integration.md](ticket-integration.md): **read it before any such write, and refuse the write if it cannot be read.** Live prompt-behavior evaluation remains a normal-session follow-up, not a blocking completion deliverable. Done only when all remaining tasks are complete, all retained tracked outputs are committed, no verified current-feature blocker remains, `review.md` and the offer have run in that order, you judge the feature complete, and the user has been shown a short completion summary and agrees.
