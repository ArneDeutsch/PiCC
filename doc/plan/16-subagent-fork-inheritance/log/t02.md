## Decisions on the "Left open" items

- **Marker field name / carriage:** a single runtime-set boolean `dispatcherIsFork`,
  carried as a **constructor option** on the Agent/Task tool definitions (not a
  closure) and spread onto the shared `dispatchOpts` so BOTH the background and
  foreground arms propagate it. Threaded exactly at the four spec'd seams:
  1. `dispatch()` opts gains `dispatcherIsFork?: boolean`.
  2. `SubagentRuntimeDeps.customToolsFor` signature gains `dispatcherIsFork: boolean`
     inserted BEFORE the optional `subCwd` (required-cannot-follow-optional, same as
     `ownerAgentId`); the per-dispatch call site passes THIS dispatch's `isFork`.
  3. `createAgentToolDefinition` opts gain `dispatcherIsFork?: boolean`; `src/index.ts`
     `customToolsFor` accepts the new param and forwards it into both the `Agent` and
     `Task` tool defs at `:702-703`.
  4. The Agent tool's `execute` puts `dispatcherIsFork: opts.dispatcherIsFork` on the
     shared `dispatchOpts`; both `...dispatchOpts` spreads (background start, foreground
     dispatch) carry it.
  Because `customToolsFor` is invoked per-dispatch, the marker scopes to THIS fork's
  tools and does not leak to the fork's normal (non-fork) grandchildren — a normal
  subagent's `customToolsFor` call passes its own `isFork` (false).
- **Notice wording:** the fork→fork refusal emits `a fork cannot spawn another fork`
  at **calm `info`** tone (by-design), distinct from t01's `... nested fork ...`
  (warning) and gate-off wording. It rides the same `FORK_DEGRADE_PREFIX`
  (`fork ran with fresh context: `) diagnostic + model-facing prompt prefix as every
  other degrade, so the developer footer + model note are identical plumbing —
  only the reason string differs, as the spec required.
- **Enforcement is via the MARKER, not depth.** The check `if (opts.dispatcherIsFork)`
  is the FIRST arm of the fork-degrade cascade at interception, so a nested fork
  (which is also `depth !== 1`) gets the precise "cannot spawn a fork" reason instead
  of the generic "nested fork" one. The depth guard (`opts.depth > maxDepth`) is left
  completely untouched as the outer backstop. The refusal takes the normal
  interception→degrade path (fresh general-purpose, no parent history seeded, no
  permission bypass).
- **A degraded fork does NOT set the marker.** The call site passes `isFork` (not the
  raw requested type), and `isFork` is true only for a fork that ACTUALLY inherits —
  so a degraded fork's granted tools stay unmarked and its own nested `"fork"` is not
  mis-refused (covered by the forkFrom-throw test).

## Resolving the t01 forkFrom-throw reorder trap

The trap: t01 finalized the fork **identity** (`resolved = buildForkAgent()`, badge
`Agent(fork)`) and called `customToolsFor` with `isFork = true` BEFORE `forkFrom` was
attempted in the later session-manager stage, so a `forkFrom` throw flipped `isFork`
to false only AFTER the fork-marked tools + fork badge were already built.

Fix — **attempt the fork-session-manager construction eagerly at interception**, in
the previously-bare `else { isFork = true }` arm:

- A fork's synthetic agent has `isolation: undefined` (shares the parent cwd) and is
  never a resume, so the cwd known at interception (`this.deps.getCwd()`) equals the
  cwd the later session-manager stage would use — construction can safely move up.
- On success: store the manager in a new `forkSession` local and set `isFork = true`.
  The session-manager stage now just **reuses** `forkSession` (reads its
  `getSessionFile()`, forces non-resumable) and never re-forks — so `h.forkCalls()`
  stays length 1.
- On throw: `isFork` stays false and `forkDegrade` is set with a GENERIC model reason
  (`forking the parent session failed`) plus the capped-error `devReason` (developer
  diagnostic only — the raw error can embed the main-session absolute path). Control
  falls through to the shared `else { resolved = general-purpose; emitForkDegrade(...) }`
  so the identity, badge, AND `customToolsFor(isFork=false)` all see the FINAL
  post-fork-attempt state. This closes t01's cosmetic `Agent(fork)`-on-throw edge:
  a forkFrom-throw now honestly badges `Agent(general-purpose)`.

`forkDegrade` was widened from `{ reason, tone }` to
`{ modelReason, devReason?, tone }` so the single interception emit site can carry
the throw case's distinct model/dev reasons; the shared `emitForkDegrade` third
param already defaults `devReason` to `modelReason`.

The old defensive `else` branch (mainSessionFile/forkSessionManager vanished between
interception and here) is kept but reworded — it is now unreachable-by-invariant
(`isFork` is only true alongside a constructed `forkSession`), retained as a
belt-and-suspenders fresh degrade.

## Tests (test/fork-nested-guard.test.ts, offline-integration via real picc())

Each scenario GUARANTEES a genuine top-level fork before exercising the nested case:
a fresh `picc()` around a fake SDK, `session_start` fired with a `sessionManager`
exposing `getSessionFile()` (so `getMainSessionFile()` returns a path), env unset,
`forkSeed` provided, dispatch at depth 1. The top result's `details.agent === "fork"`
+ `inheritedMessageCount === SEED.length` assert the fork is genuine (non-vacuous).

1. **fork→fork refused** — drive the top fork's granted Agent tool with
   `subagent_type: "fork"`; assert the nested `details.agent === "general-purpose"`,
   the notice contains `a fork cannot spawn another fork` (and NOT the nested/gate
   wording), `inheritedMessageCount === 0`, and `forkCalls()` stayed length 1 (the
   refusal short-circuits before forkFrom).
2. **fork→normal allowed** — nested `subagent_type: "general-purpose"` completes with
   no fork-degrade notice; `forkCalls()` length 1.
3. **forkFrom-throw degrade** — `transformSdk` makes `forkSessionManager` throw; the
   top degrades to `general-purpose` (honest badge) with the forkFrom-throw notice,
   and its nested `"fork"` degrades via the NESTED reason (not "cannot spawn a fork"),
   proving unmarked tools.
4. **coordinator can still fork** — a non-fork dispatcher's `"fork"` is honored
   (marker is per-dispatch, never global).

## Deviations / friction / notes

- **forkFrom placement — orphan-file hazard, and its fix (review).** `forkFrom`
  (`SessionManager.forkFrom`) is EAGER + SYNCHRONOUS: it writes a full copy of the
  parent conversation to disk the instant it is called. The initial t02 implementation
  ran it at the INTERCEPTION point — BEFORE the three early-return gates
  (abort-before-start, SubagentStart-block, abort-after-worktree) — so an aborted or
  hook-blocked fork left an uncleaned on-disk copy of the entire parent conversation,
  and a `SubagentStart` hook that blocked the dispatch no longer stopped the seed from
  hitting disk. The construction has been RELOCATED (see Review fixes) to immediately
  before `customToolsFor`, AFTER all three gates, so no file is ever created for an
  aborted or blocked dispatch. It still runs before `customToolsFor`, so the trap fix
  holds. Accepted cosmetic (documented, not fought): in the rare `forkFrom`-THROW case
  the `SubagentStart` hook payload may report the requested `"fork"` subagent_type
  (SubagentStart fires before the throw is known); the RESULT badge stays honest
  (`general-purpose`). t01's no-leakage invariant is unchanged (hook payloads carry the
  task text only; inherited history lives in the seeded session, never in a payload).
- **Degraded-fork resumability drifted (benign).** In t01 a forkFrom-throw ran
  in-memory/non-resumable because the throw happened inside the fork session-manager
  branch (sessionManager left undefined → in-memory fallback). Now the throw degrades
  at interception, so the run takes the ordinary general-purpose path — persisted +
  resumable when the SDK supports it, in-memory otherwise. This is correct: a degraded
  fork is a genuine fresh general-purpose run with no inherited context, so being
  resumable is honest. No t01 test asserted the old in-memory posture (only
  `isFork` falsy, fresh, warning notice, no-path-leak — all still hold).
- **`deny: Agent(fork)` cross-check** is a permission-layer concern (gating the tool
  call before dispatch), orthogonal to the marker; not separately added here (the spec
  marked it "may live in t01's tests"). It is not an acceptance criterion for t02.

## Review fixes

Four fixes applied on review; the marker-threading seams, depth guard, env gate,
exfiltration guard, and enforcement-arm ordering are all UNCHANGED — only the
PLACEMENT of the `forkFrom` construction and the tests + log moved.

- **FIX 1 — relocated the eager `forkFrom` construction (the orphan-file bug).**
  `forkFrom` is eager + synchronous (writes the full parent conversation to disk on
  call). It was RELOCATED out of the interception `else` arm to run immediately before
  `customToolsFor`, AFTER all three early-return gates (abort-before-start,
  SubagentStart-block, abort-after-worktree) — so an aborted or hook-blocked fork never
  creates the on-disk copy. Mechanism (chosen fix, NOT dispose-on-early-return):
  - At interception the genuinely-inheriting `else` arm no longer calls `forkFrom`; it
    sets `isFork = true` tentatively and stashes the call in a captured thunk
    `attemptForkSession(cwd)` (capturing the loaded fork SDK + the narrowed
    main-session file). A fork shares the parent cwd (isolation undefined) and is never
    a resume, so the dispatch `cwd` passed to the thunk equals the interception cwd.
  - Just before `customToolsFor`, `attemptForkSession(cwd)` runs once. On SUCCESS
    `forkSession` is set and `isFork` stays true (the session-manager stage REUSES it,
    never re-forks — `forkCalls()` stays 1). On THROW it flips `isFork = false`,
    re-resolves the identity (`agent = resolveAgent(builtins, "general-purpose")` — the
    `const agent` became a typed `let`), and emits the generic model reason
    (`forking the parent session failed`) with the capped raw error on the developer
    diagnostic only. So the FINAL `isFork` + identity/badge are settled before the
    child tools + identity are built (trap fix intact; fork-nested-guard test 3 passes).
  - The env=0 / nested / no-transcript / SDK-can't-fork / fork-spawns-fork degrades
    stay resolved at interception (they never needed `forkFrom`). `granted` is computed
    from the (identically all-tools) fork/general-purpose agent, so a throw-degrade
    grants no wider tool set. The session-manager fork branch and its defensive
    fallback are unchanged (comments updated to say "just before customToolsFor").
  - Accepted cosmetic: a `forkFrom`-throw fires `SubagentStart` with the `"fork"`
    subagent_type (before the throw is known); the RESULT badge stays `general-purpose`.
- **FIX 2 — added the missing per-dispatch scoping regression test.** New test:
  genuine top-level fork (depth 1, inherits) → NORMAL `general-purpose` child (depth 2)
  → that child dispatches `subagent_type:"fork"` (grandchild, depth 3). Asserts the
  grandchild degrades via the DEPTH/`nested fork` wording (NOT `cannot spawn a fork`),
  proving the fork's normal child's tools stayed UNMARKED — i.e. the call site threads
  the RECOMPUTED `isFork`, not `opts.dispatcherIsFork`, into `customToolsFor`. Needs a
  3-level chain, so the test raises the fixture's `subagents.maxDepth` (2 → 3) around
  the run and restores it (fixture dir is shared; picc() reads maxDepth once). The
  harness `wireFork` gained a second optional action (`nestedAction2`) fired from the
  2nd Agent-bearing session; existing tests are unaffected.
- **FIX 3 — added an orphan-file lock-in test.** A `"fork"` dispatch ABORTED before
  start (an already-aborted signal passed to the foreground Agent tool) surfaces on the
  isError channel and leaves `forkCalls()` EMPTY (the load-bearing regression signal —
  before relocation `forkFrom` ran at interception, before the abort gate) and creates
  NO `*.subagents` transcript dir/file. Offline the fake `forkSessionManager` writes no
  real file, so the empty-`forkCalls()` assertion is what actually catches a regression;
  the dir check locks in the on-disk consequence.
- **FIX 4 — corrected this log.** Replaced the earlier "Accepted — benign orphan (block
  path only)" note with the accurate eager+synchronous account and this Review fixes
  section.
