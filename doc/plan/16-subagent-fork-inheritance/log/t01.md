## Decisions on the "Left open" items

- **Synthetic fork-agent name / badge label:** the fork agent's `name` is `"fork"`.
  A successful inherited fork therefore badges `Agent(fork) completed`; a degrade
  runs the built-in `general-purpose`, so its badge reads `Agent(general-purpose)`.
  **The reliable cross-surface discriminator is the degrade FOOTER line** (rendered
  on both the foreground Agent result and the background TaskOutput result). The
  distinct badge only holds on the **synchronous** path: there `renderAgentResult`
  badges `details.agent` = the fork's `agentName`, so a successful fork reads
  `Agent(fork)` and a degrade reads `Agent(general-purpose)`. On the **background
  (default) path** the result badge derives from the raw requested `subagent_type`
  (`"fork"`), so BOTH a successful and a degraded background fork badge `Agent(fork)`
  — only the footer distinguishes them there. The **forkFrom-throw foreground case**
  also still badges `Agent(fork)` (the fork tools/identity were already built before
  the throw was discovered), honest only via the footer — to be closed in t02.
- **Notice wording (per trigger):** all fork degrades emit a single diagnostic
  `fork ran with fresh context: <reason>` (the `FORK_DEGRADE_PREFIX` sentinel) plus
  a model-facing prompt prefix `(PiCC: this "fork" dispatch ran with FRESH context
  — it did NOT inherit … Reason: <reason>.)`. Reasons + tone:
  - env off → `fork inheritance is disabled via CLAUDE_CODE_FORK_SUBAGENT; unset it
    to enable` (calm `info` — names the variable and the fix, WITHOUT hardcoding
    `=0`, since `isEnvTruthy` treats `0/false/no/off/""` all as off).
  - non-main-session (`depth !== 1`) → `the parent conversation is not available for
    a nested fork (only the main session can fork)` (`warning`).
  - no transcript → `no parent transcript is available to fork
    (print/headless/no-session mode)` (`warning`).
  - SDK load failed (`await this.sdk()` rejected) → `the fork runtime could not be
    loaded` (`warning`); SDK loaded but lacks the method → `this runtime cannot fork
    a session (the SDK lacks forkSessionManager)` (`warning`).
  - `forkFrom` threw → model-facing reason is the GENERIC `forking the parent
    session failed` (no raw error/path); the developer diagnostic keeps the capped
    `forking the parent session failed (<capped error>)` (`warning`).
- **Persisted vs in-memory:** default = **persisted child file** (a brand-new file
  from `SessionManager.forkFrom`), forced **non-resumable**. Asserted explicitly:
  the real-SM test reopens the child file and finds the inherited token; the
  returned result reports `resumable:false` with a defined `transcriptPath`;
  SendMessage refuses it.

## How "isFork" is computed / degrade visibility

- `isFork` is true only when `requested === "fork"` AND gate on AND the dispatcher
  is the main session AND a parent transcript is present AND the SDK exposes
  `forkSessionManager`. The main-session predicate is the EXACT `opts.depth === 1`
  (the degrade check is its exact complement `opts.depth !== 1`, so a hypothetical
  depth-0 dispatch also degrades — not `depth > 1`). The main session's Agent/Task
  tools dispatch at depth 0→1, so a main-session dispatch is exactly
  `opts.depth === 1` (verified in `src/index.ts` — the tool is created with
  `{ depth: 0 }` and `execute` dispatches at `opts.depth + 1`).
- The gate is read from `process.env.CLAUDE_CODE_FORK_SUBAGENT` ONLY (never
  `project.settings.env`), via `isEnvTruthy`; unset ⇒ enabled.
- Interception sets `resolved` (fork agent when honored, built-in general-purpose
  when degraded) so the generic `unknown subagent_type "fork"` warning can NEVER
  fire — proven by a runtime-core test and the fork-inheritance suite.
- **Developer-facing degrade travels via `details.diagnostics`.** `background-tasks.ts`
  is read-only for this task, so rather than add a new result field that only the
  foreground path would carry, the degrade rides the existing `diagnostics` channel
  that BOTH the foreground Agent result and background TaskOutput result already
  forward. `renderAgentResult` scans `details.diagnostics` for the sentinel prefix
  and renders a muted (calm) / warning-colored footer line.

## Deviations / friction / notes

- **`opts.agentOverride` untouched:** the fork agent is assigned to the LOCAL
  `resolved`/`agent`; `overrideDispatch` stays false. `resumable` is forced false in
  the fork branch AND the register gate is extended to `overrideDispatch || isFork
  ? false : resumable`.
- **Early SDK load for forks:** to know `forkSessionManager` presence (degrade
  trigger iv) before `customToolsFor`, a `"fork"` dispatch now `await this.sdk()`
  once at interception (guarded — a loader failure degrades to fresh). This is the
  cached promise the later `await this.sdk()` reuses; non-fork dispatches are
  unchanged.
- **`forkFrom`-throws (trigger v) is the one late-discovered degrade.** It is
  detected at the third session-manager branch (after `customToolsFor` already ran
  with `isFork = true`). The session degrades correctly (fresh in-memory context,
  warning notice, footer, `isFork` flipped false, `resumable:false`), but the
  already-built tools carry the fork marker and the badge still reads `Agent(fork)`
  for this rare case. Acceptable: t02's fork-spawns-fork guard is not built yet, and
  the footer honestly marks the degrade. Documented here as a known minor edge.
- **SendMessage refusal reason** was generalized: a fork persists a transcript yet
  is non-resumable, so the old "ran without a persisted transcript" wording would
  mislead. The refusal now branches on `record.transcriptPath` to give a truthful
  reason (`its context cannot be safely re-derived (e.g. a fork's inherited parent
  conversation …)`). No registry `isFork` flag was added (out of the writable
  surface for `subagent-registry.ts` beyond what already exists; the transcript
  presence is a sufficient discriminator).
- **Fake SDK seed:** `forkSessionManager` was added to both the fake SDK and the
  real-SessionManager seam. The fake fork manager tags its returned manager with a
  captured `__forkSeed`; `createAgentSession` pre-populates `state.messages` +
  `inheritedMessageCount` ONLY from that marker, so ordinary persisted/reopened
  managers (t02/t04 resume) are untouched — no regressions.
- **No leakage:** the fork's `SubagentStart` payload `prompt` is the task text only
  (parent history lives in the seeded session messages, never in hook payloads) —
  asserted by a unit test.

## Review fixes

Small, low-risk fixes applied on top of the original t01 implementation (all in the
fork dispatch path; nothing else changed):

1. **[security] No parent absolute-path leak into the model prompt on forkFrom-throw.**
   The forkFrom-throw degrade previously injected the raw capped error (which can
   embed the main-session absolute path) into the fork's OWN prompt (model-facing).
   Now the model-facing prefix uses a GENERIC reason (`forking the parent session
   failed`, no error detail); the capped `capErrorText(...)` detail rides the
   developer-facing `diagnostics` entry ONLY. New assertions in the "forkFrom throws"
   test: the model prompt contains the generic reason but neither the raw error text
   nor the path; the diagnostic keeps both.
2. **[cleanup] De-triplicated the degrade emission.** Extracted a local
   `emitForkDegrade(tone, modelReason, devReason?)` helper so the model-facing prompt
   prefix + the `FORK_DEGRADE_PREFIX` diagnostic are produced in ONE place and can't
   drift across the three degrade sites (gate/nested/no-transcript/no-SDK, forkFrom-
   throw, defensive). The helper lets the model text differ from the developer detail
   (throw case, fix #1). The `isFork = false; resumable = false` side effects stay at
   the two late call sites.
3. **[parity] Exact main-session predicate.** Nested-degrade check changed from
   `opts.depth > 1` to `opts.depth !== 1` (exact complement of the `=== 1` honor
   condition; a hypothetical depth-0 dispatch also degrades). Updated the nearby
   comment and this log accordingly.
4. **[ux] Env-off notice no longer hardcodes `=0`.** `isEnvTruthy` treats
   `0/false/no/off/""` all as off, so the notice now reads `fork inheritance is
   disabled via CLAUDE_CODE_FORK_SUBAGENT; unset it to enable` (still names the
   variable + the fix). Tests updated (`fork-inheritance.test.ts`: the env-off unit
   test now asserts the variable is named but `=0` is NOT, and the render-footer test
   string was updated).
5. **[coder] SDK load-failure reason accuracy.** If `await this.sdk()` REJECTS (the
   SDK failed to LOAD), the reason is now the truthful `the fork runtime could not be
   loaded`; the genuine "loaded but no method" case reads `this runtime cannot fork a
   session (the SDK lacks forkSessionManager)`. Tracked via a `forkSdkLoadFailed`
   flag in the interception guard.
6. **[log] Corrected the badge claim** (see the "Left open" badge bullet above): the
   FOOTER line is the reliable cross-surface discriminator; the distinct badge only
   holds on the synchronous path (background badges derive from the raw requested
   `subagent_type` so both success and degrade badge `Agent(fork)`); the forkFrom-
   throw foreground case also badges `Agent(fork)` (to be closed in t02).
