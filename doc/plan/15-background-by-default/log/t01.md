## `run_in_background` typing / coercion — DECISION
- Kept `!== false` rather than normalizing a non-boolean. Rationale: on an ambiguous/non-boolean
  value (e.g. stringy `"false"`), `!== false` fails toward **background**, i.e. toward the new
  default — acceptable.
- Coercion finding: grepped `src/` for `Value.Cast|Value.Convert|Value.Decode|Value.Clean|
  TypeCompiler|coerce` — **no TypeBox coercion helpers are present in the repo**. No evidence Pi
  coerces `execute()` params to the tool's TypeBox schema before handing them over, so a
  non-boolean could in principle reach the handler unchanged. Assumption recorded; `!== false`
  is safe under it (ambiguous → new default). Not worth deeper investigation for t01.

## Review-fix batch (accepted fixes, applied after initial t01)
1. **(parity SHOULD + UX NIT) Agent/Task tool `description` reword** (`subagents.ts` ~1443). The
   old "(or wait for the settlement notice)" read as a same-turn peer of TaskOutput; PiCC delivers
   that notice only on a *later* turn, so a Claude-trained model could dispatch + finalize expecting
   a same-turn result. Reworded to make TaskOutput the unambiguous active-collection path with the
   settlement notice explicitly a later-turn arrival: "...collect the result with TaskOutput before
   you rely on it or finalize an answer (a settlement notice also arrives on a later turn). Pass
   run_in_background: false ...". Description anti-regression test (`background-tasks.test.ts:1008`)
   stays green — still matches `/background by default/i`, `run_in_background: false`, `TaskOutput`.
2. **(UX NIT) Background start message timing cue** (`subagents.ts` ~1558). Appended "before
   finalizing" so the dispatch-time string is self-sufficient: "...to retrieve the result before
   finalizing." No test asserted the trailing period, so this is non-breaking (the existing e2e/unit
   checks match `Background task ... started` and `TaskOutput` substrings).
3. **(UX NIT) HARNESS_CONVENTIONS consequence clause** (`context-assembly.ts:104`). Added the
   silent-loss consequence: "...collect each result with TaskOutput before you rely on it or finalize
   an answer — otherwise its result is lost (or pass run_in_background: false ...)." Kept tight (one
   em-dash clause) since this string is emitted every turn.
4. **(coder NIT) Stale header comment** (`background-tasks.ts` ~18). Rewrote the doc comment: it now
   says a background dispatch from the Agent tool registers the un-awaited dispatch here and that
   post-F15 the common path is an Agent call that *omits* `run_in_background` (explicit `true` routes
   here too). Comment only, no logic change.
5. **(tester SHOULD) Replaced vacuous sanitization assertion** (`background-tasks.test.ts` ~824).
   The old `expect(JSON.stringify(out)).not.toContain(ESC)` could never fail (JSON.stringify escapes
   U+001B to a `` sequence, and the *completed* path never puts the agent type into TaskOutput
   `content`). Replaced with a real default-path proof: within the same test, drive a FAILED
   default-path task (omitted `run_in_background`, hostile ESC-laden `subagent_type`, depth 5 → dispatch
   depth exceeds maxDepth → `ok:false`). The failed-path TaskOutput `content` interpolates the agent
   label into its subject (`background-tasks.ts:681/701`), so `failOut.content[0].text` genuinely
   exercises label sanitization; asserted it is ESC-free (plus status `failed` and defaulted-background
   start message). The genuine settlement-notice sanitization guard (`notices[0]).not.toContain(ESC)`
   ~816) is untouched.
6. **(tester SHOULD) Anti-regression on the highest-leverage nudge** (`runtime-core.test.ts:207`).
   Extended the existing conventions-present test with `expect(suffix).toMatch(/background by default/i)`
