## Phase 4 (HOW investigation) findings

- 2026-07-15 **Baseline mismatch (surface to user):** Claude Code ~2.1.x *removed* MultiEdit (about v2.0.8, Oct 2025). Implementing it is a *superset* of the pinned baseline, justified by older-project compat (projects still carry `MultiEdit` in permission rules / hook matchers / subagent `tools:`; primed models still emit the call). Registry note must carry the honesty hedge — `full` means "faithful to the pre-removal contract", not "matches current Claude Code". Sources: code.claude.com tools-reference (no MultiEdit row), wong2 authentic-tool-prompt gist, anthropics/claude-code #11125 & #8994.
- 2026-07-15 **Semantics settled (authentic historical MultiEdit contract):** exact string match (NO fuzzy — Pi's `edit` fuzzy-normalizes smart quotes/dashes/whitespace; MultiEdit must be exact); sequential against a running buffer; per-edit `replace_all` with unique-else-error evaluated on the running buffer; empty `old_string` = file-creation idiom (first edit on a nonexistent file); `old_string === new_string` rejects; empty `new_string` is a valid deletion; atomic (any miss rejects whole batch, file untouched).
- 2026-07-15 **Permission parity already in place (verified in code):** `permissions.ts:112` `FILE_EDIT_TOOLS = {Edit, Write, MultiEdit, NotebookEdit}` + `ruleToolMatches` (one-directional) means an `Edit(...)` deny/allow rule already gates MultiEdit; `pathSpecifierMatches` has a `case "MultiEdit"` (:564) reading `file_path`. No `permissions.ts` change needed. `permissions-hardening.test.ts` already proves it. (coder initially claimed Edit rules won't cover MultiEdit — refuted by reading the engine; claude-parity + security were correct.)
- 2026-07-15 **MUST constraint — resolution consistency:** resolve the write path with the SAME rule the guard matches on: plain `path.resolve(getCwd(), file_path)`. Do NOT adopt Pi's `resolveToCwd` (`~`/unicode-space/`@`/`file://` transforms) — a divergence between the *written* path and the guard's *evaluated* path is a path-scoped-deny bypass (e.g. `~/.ssh/...`). This pre-existing gap also affects Pi's own Edit/Write but MultiEdit must not add to it.
- 2026-07-15 **MUST constraint — concurrency/abort:** reuse the exact exported `withFileMutationQueue` (module-level Map keyed on realpath; shared by Pi edit+write, so cross-tool same-file writes serialize). Read-once → compute-all-in-memory → single `writeFile`; never write-per-edit. Check `signal.aborted` after each await; do not reject from an abort event listener (would release the queue mid-op). No temp-file+rename — match Pi's atomicity level, don't over-claim.
- 2026-07-15 **Public export surface correction:** `generateDiffString`/`generateUnifiedPatch` ARE public (reusable for a `details.diff`/`patch` matching Pi edit's hook-payload shape); only the *matching* helpers (`applyEditsToNormalizedContent`, `stripBom`, `normalizeToLF`, `restoreLineEndings`, `detectLineEnding`) are private and must be reimplemented.

PiCC enforces no such freshness guard across the whole Edit/Write/MultiEdit family (all tagged `full`). Best resolved once family-wide — implement the guard, or disclose the divergence registry-wide — not inside F17. (claude-parity, Phase 8)

- **Edit exactness audit:** registry claims `tool.Edit` is "exact-string" but Pi's `edit` fuzzy-normalizes on a miss. Worth verifying the claim actually holds / correcting the note. (claude-parity)
- **`examples/full-surface` MultiEdit fixture:** the sample project exercises Edit/Write but never MultiEdit; a call site + an "Edit(...) rule gates a MultiEdit call" assertion would lock in the namespace behavior end-to-end. (claude-parity)
- **`touchedFilePath` also omits `NotebookEdit`:** low impact (it's a degraded no-op) but the same defense-in-depth injection gap. (security)

- **No-op → real-writer posture change:** projects that implicitly relied on MultiEdit degrading to a no-op as a safety net now face a real writer; their `Edit`/`MultiEdit` deny rules do hold (via the expansion above). Call this out in docs. (security)
