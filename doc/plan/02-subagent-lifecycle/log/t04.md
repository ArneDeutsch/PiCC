## Decisions on "Left open" items

- **Tool parameter shape:** `SendMessage({ to, message })` — matches Claude Code
  (`to` = agent ID or name; `message` = the follow-up/steer text). No extra
  params. `to` is validated by registry lookup only (SEC #2).
- **Steer vs followUp:** `steer()` for a running background dispatch (it is
  literally a "steering message" = mid-task course correction). Finished agents
  are re-dispatched (reopen + prompt), not `followUp`'d (their session is gone).
- **Ack wording:**
  - Resume: `Agent <id> resumed in background as <task-id>. Its result will
    arrive via TaskOutput (task_id "<task-id>") or at your next turn.`
  - Steer: `Message delivered to running agent <id> as a mid-task course
    correction.`
  Both are model-visible tool-result text (never `details`-only — the round-1
  plan-review MUST-FIX that the ID must live in text the model reads).

## SEC #1 — resume is a FULL re-dispatch (shared construction path)

Resume calls the SAME `SubagentRuntime.dispatch()` as the initial dispatch, with
a new `opts.resume = { transcriptPath, cwd, worktreePath }`. Everything after
resolution — `gateTools`, `customToolsFor`, `createGuardExtension`,
`createMaxTurnsExtension`, `buildSystemPrompt`/skill+agent lockdown, model/effort
resolution, scoped hooks + `injectIdentity`, depth, subCwd — runs through the
identical code. `opts.resume` changes ONLY two things:
1. worktree: skip `worktrees.enter()`; reuse `resume.cwd`/`resume.worktreePath`.
2. session manager: `sdk.reopenSessionManager(transcriptPath, dir, cwd)`
   (`SessionManager.open`) instead of `persistedSessionManager` (`create`).
There is no second, lighter dispatch path. Test asserts the resumed dispatch's
`createAgentSession` options (tools list, customTools, resourceLoader
extensionFactories = guard + maxTurns, model) are identical to the original's,
and that depth is preserved (via the reused `depth`).

## SEC #2 — `to` resolves registry-only

`SubagentRegistry.resolve(to)` is pure in-memory Map lookups: `isAgentId(to)` →
`records.get(to)`; else `nameIndex.get(to)`. A hostile `to` (`..`, separators,
absolute path) is never an agent-ID and never a registered name → registry miss →
clean "unknown address" error. The transcript path used for reopen comes from
`record.transcriptPath` (captured from the REAL persisted manager's
`getSessionFile()` at dispatch time), NEVER string-assembled from `to` and NEVER
a fresh on-disk resolver scan (addresses the t02 "plantable .subagents dir"
security note — the registry's recorded path is the only trusted source). Test
feeds `..`/`/etc/passwd`/`C:\evil`/`agent-x/../y` and asserts no fs access + a
clean error.

## Name integrity (2.1.199)

`nameIndex: name -> { firstId, currentId, rebound }`. A second dispatch reusing a
name sets `rebound=true`. Resolving by that name then refuses ("the name 'X' now
reaches <currentId>; address it by agent id"). IDs always disambiguate. The
registry is per-orchestrator-session, so the check is inherently session-scoped.

## Resume policy on failed-with-partial (t02 deferral resolved)

t02 shipped the `resumable` trailer on failed-with-partial runs and deferred to
t04 whether they are actually resumable. Decision: KEEP them resumable — a
coordinator following up on a cut-off run with its prior context is exactly the
dogfooding scenario that motivated this feature. The registry record carries the
same `resumable` the dispatch computed; SendMessage refuses only genuinely
non-resumable records (one-shot builtins, in-memory fallback, no transcript).

## t05 hand-off (settled-notice dedup)

Each record carries `settledNoticeConsumed`. `register()` (initial AND resume)
sets it to `false`; `markSettled()` leaves it false (un-consumed). `consumeSettledNotice(id)`
returns true exactly once per settlement. So a resume RE-ARMS the notice — t05
emits exactly one notice per settlement of the same ID. t04 asserts the resumed
run's settlement leaves the notice un-consumed (re-armed).

## Out of scope (recorded for t07)

Cross-restart resume: the registry is process-lifetime. A resume after a PiCC
restart misses the registry → clean unknown-address error. t07 records the
SendMessage registry entry as `partial` naming this.

## Steer reaches only background dispatches (by design)

A foreground `Agent` call blocks the parent's turn, so the coordinator cannot call
SendMessage while a foreground dispatch runs — steering de-facto reaches only
BACKGROUND dispatches. Once ANY dispatch (foreground or background) settles and is
resumable, SendMessage CAN resume it. Not a defect; stated in the tool description
and the SendMessage doc-comment.

## Subagents never get a SendMessage channel

SendMessage is registered ONLY on the parent session (index.ts, next to
Agent/Task). It is never built in `customToolsFor` (one-line guard comment added).
Belt-and-braces: even though "SendMessage" is now in `allKnownToolNames` (so an
inherit-all subagent's gate lists it), `claudeToolsToPiBuiltins` maps it to no Pi
builtin and `customToolsFor` has no branch that constructs it — so a subagent's
session never receives it. No subagent→subagent or subagent→parent channel.

## Deviations / surprises

- No spec deviations. Writable surface honored (new registry module earned its own
  file per the spec's "if the registry deserves its own module").
- The fake `DefaultResourceLoader.reload()` is a no-op and never invokes
  `systemPromptOverride`, so the SEC #1 test asserts prompt/lockdown identity by
  invoking the captured `resourceLoader.options.systemPromptOverride()` directly
  (encoding depth into the string) rather than spying on `buildSystemPrompt` calls.
- A resume that cannot reopen (missing `reopenSessionManager`, or `open` throws)
  returns a LOUD failed DispatchResult — never a silent fresh in-memory run, which
  would drop the agent's prior context (the exact bug class this feature fixes).

  at dispatch time), NOT a fresh `resolveSubagentTranscript` on-disk scan — directly
  answering the t02 security note about plantable `.subagents` files.
- Cross-restart resume is out of scope (registry is process-lifetime) — t07 should
  record the SendMessage registry entry as `partial` naming this.
