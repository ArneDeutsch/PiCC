# t01 execution log — Registry ownership + scoped view

## Decisions on "Left open" items

- **`start()` addition form:** chose a **6th positional `owner?: string`** (over an
  options bag). Rationale: `start()` already has 5 positional params (`label`,
  `promise`, `abort?`, `agentId?`, `agentType?`) all threaded positionally by the
  Agent tool; appending one more positional keeps the existing call sites
  compiling untouched with `owner` defaulting to `undefined` (coordinator/owns-all),
  and matches the surrounding idiom. An options bag would have forced a call-site
  rewrite that t02 would then have to touch — out of scope here.
- **Scoped-view representation:** a **closure object literal** returned from
  `scopedTo(ownerId)` (not a small class). It closes over the live registry via
  `this` (arrow-function members preserve `this` lexically) and a private
  `owns(id)` helper checking `this.tasks.get(id)?.owner === ownerId`. This keeps
  the view a plain `BackgroundTaskView` value with no new named type to export,
  and — critically — every member reaches `this.tasks` / the public methods **at
  call time**, so delegation is live (no construction-time snapshot). Did not
  memoize per owner (not required; t02 builds the view once per dispatch anyway).

## What changed

- `src/runtime/background-tasks.ts`:
  - `BackgroundTaskRecord.owner?: string` added, with a doc comment stressing
    `owner` (dispatcher) ≠ `agentId` (dispatched child).
  - `start()` gained a 6th positional `owner?` and sets `record.owner`.
  - New exported `BackgroundTaskView` interface declaring exactly the five members
    the tools consume (`get`, `ids`, `wait`, `stop`, `subscribeProgress`).
  - New `scopedTo(ownerId): BackgroundTaskView` method; filters all five members
    on `owner === ownerId`; foreign/unknown ids get the unknown-id shape with no
    delegation to `registry.stop`/`abort` and a no-op `subscribeProgress` unsub.
  - Retyped `unknownIdError(view: BackgroundTaskView, id)` and both factory params
    (`createTaskOutputTool` / `createTaskStopTool`) from the concrete class to
    `BackgroundTaskView`. **No factory body changes** — scoping lives entirely in
    the view. Deliberately did NOT close over the full registry for
    `unknownIdError` (that would relist foreign ids and reopen the leak).
- `test/background-tasks.test.ts`: new `describe` block with the full set of t01
  cases (own-reachable, live-delegation, foreign-refused it.each, scoped
  known-ids, no-live-progress-leak, no-effect-after-refused-TaskStop,
  coordinator-unscoped-reaches-all, grandchild-shape).

## Friction / surprising

  the coordinator-supplied *absolute* paths under the main repo root
  (`F:\Arne\Projekte\picc\doc\...`) 404'd — they only exist on the feature branch

- Non-leak subtlety worth recording: `unknownIdError` echoes the **requested**
  id (`Unknown task_id "<id>"`), so a foreign-request error and a truly-unknown
  error differ in that echoed id for a benign reason (the caller supplied it).
  The indistinguishability the feature guarantees lives in the **"Known
  background tasks:" segment** (scoped `ids()`), which the tests assert is
  byte-identical between the foreign and unknown cases — not the whole message.
- Foreign "running" tasks in the tests use a gate that is never released. This
  doubles as a leak tripwire: a scoped `wait`/`subscribeProgress` that wrongly
  delegated to the foreign record would hang the test rather than silently pass.

  anchored on the file's final lines. No effect on the result.
